Release decision

The working tree clears the first foundation gate, but it is not the finished production seed. The reproducible install, dependency, mutation-boundary, lint, type, test, build, and high-severity audit checks are green. Complete the remaining runtime-boundary, security-header, architecture, migration, and documentation work before broad adoption.

Top structural recommendation

Turn the example feature into one deep, feature-owned module and retire the global type/constant/enum registries. This improves depth, narrows each public interface, keeps implementation details local, and creates an honest seam for Next.js adapters and tests.

Current architecture: many surfaces, little depth

The core create flow crosses six modules. Most layers add translation or error-shape ceremony rather than hiding substantial implementation complexity. Meanwhile, unrelated features converge on three global registries.

flowchart LR
  UI[Example form] --> A[Server Action adapter]
  A --> AB[Generic action wrapper]
  AB --> S[Example service]
  S --> D[Example DAL]
  D --> DB[(Drizzle / Postgres)]
  T[Global types.ts\n59 exports] -. imports .-> UI
  T -. imports .-> A
  T -. imports .-> S
  T -. imports .-> D
  C[Global constants.ts\n21 exports] -. policy .-> UI
  E[Global enums.ts\n17 exports] -. policy .-> A

Low leverage seams

The service validates input already validated by the action, delegates to one DAL call, and maps one date. The DAL wraps one query. Each interface is almost as complex as its implementation, so the modules are shallow.

Poor locality

types.ts imports the database schema and feature schema, owns UI props and analytics payloads, and even declares IBreadcrumbItem twice. A small feature edit requires navigating global registries.

History signal: package configuration, CI, Next config, global types, constants, and the lockfile are the most frequently changed files in the last 40 commits. There is no CONTEXT.md or ADR directory explaining the load-bearing choices.

Architecture candidates

These are directions, not premature API designs. Each recommendation states the seam to improve and the deletion test used to challenge it.

Candidate 1 · Top recommendation

Own domain concepts inside feature modules

Recommendation: StrongLocalityDepth

Move example records, inputs, errors, validation, mapping, and persistence details behind one feature-owned public interface. Keep cross-feature primitives global only when multiple real consumers prove the need. Next.js routes and actions remain thin adapters.

Before

Every feature imports global types, enums, constants, errors, a service, and a DAL. Implementation details flow upward into registries.

→

After

A feature module hides validation, persistence, mapping, and domain failures. Adapters depend on one narrow public seam.

flowchart LR
  R[Next route adapter] --> M[Examples module\nsmall public interface]
  A[Server Action adapter] --> M
  M --> I[validation + policy + mapping\nprivate implementation]
  I --> DB[(database)]
  X[Other features] -. do not import internals .- M

Deletion test: if the global registries disappeared, only real cross-feature contracts would need a new home; most feature code would become easier to find. Payoff: future auth, caching, events, and alternative adapters can change behind one seam.

Candidate 2

Collapse the ceremonial example layer chain

Recommendation: StrongYAGNISeam

Keep a layer only when it hides a volatile implementation, enforces domain policy, or serves multiple adapters. Today the service and DAL mostly relay a single operation and duplicate parsing.

Before

UI → action → generic wrapper → service → DAL → database

→

After

Next adapter → deep feature module → database adapter

Deletion test: removing the pass-through service layer changes call sites but not product behavior. Keep a database adapter only when it enables a meaningful test or infrastructure substitution.

Candidate 3

Use one failure model at the feature boundary

Recommendation: StrongShrink

The code currently carries IFetchResponse, TResult, IError, IAppError, form responses, neverthrow results, and exception wrappers. Choose one internal failure representation per deep module; translate once at HTTP/form adapters.

Before

Errors are wrapped, mapped, logged, rewrapped, and sometimes thrown. Raw exception messages can reach form clients.

→

After

Private implementation failures → stable module failures → adapter-safe messages/status.

Deletion test: remove unwrapResultOrThrow and overlapping wrappers; callers that genuinely require exception semantics will identify the actual boundary. The "never throw anywhere" rule should not force wrappers at process/config boundaries.

Candidate 4 · Ponytail audit

Make optional capabilities opt-in

Recommendation: StrongDeleteNative

A generic seed should have a small trusted core. A static reference scan found at least 848 lines of unwired telemetry and helper modules, before speculative SEO and UI primitives. Keep recipes or add-on templates for GA, Sentry, database, cookie helpers, retry/batch helpers, and vertical-specific schema.

Before

Every generated app inherits unused code, dependencies, environment variables, docs, and security decisions.

→

After

Minimal core + tested optional capability packs selected when a project actually needs them.

Documentation findings at audit time

Contradictions found in the baseline

  • llms.txt says dynamic OG images exist; no OG image route exists.
  • Architecture docs list AI_CRAWLERS integration; robots rules are hardcoded and the constant is unused.
  • SEO code advertises /logo.png and /search; neither resource exists.
  • Testing docs reference Testing Library packages that are not installed.
  • GA docs say server sending catches failures; its fetch can reject.
  • README/AGENTS describe automated testing in CI; the test step is commented out.

Rules that harm the architecture

  • "All types/constants/enums in one file" destroys feature locality and grows shallow registries.
  • "Never throw" is too broad for process/config boundaries and produces adapter ceremony.
  • "Every app value must be global" turns local implementation details into shared interfaces.
  • Mandatory atomic-design folders classify component size without improving module depth.
  • "Fix every pre-existing warning immediately" expands read-only or scoped tasks without user authority.
  • Universal API/DAL/service rules prescribe layers before the domain earns them.

Unslop standard: remove claims like "modern best practices," "production-ready," and "type-safe" unless an executable check or runtime boundary proves them. Prefer a short statement of what the starter guarantees, what is optional, and what adopters must choose.

Recommended sequence

Completed — stabilize the seed

Next and Drizzle are patched, the lockfile is reproducible, the mutation path fails closed, and the environment contract is aligned. Runtime entry-point separation remains in the next slice.

Completed — make the gate honest

Bun is pinned; CI uses the frozen install path, complete lint coverage, native route types, tests, a production build, and a high-severity audit.

Shrink before reorganizing

Delete dormant modules, duplicate barrels, vertical-specific SEO, and false documentation. A smaller codebase makes the true boundaries visible.

Deepen the first feature

Move feature concepts beside their implementation, collapse pass-through layers, choose one failure model, and test through the feature seam. Use this as the pattern for subsequent domains.

Record decisions, not inventories

Write a short context map and a few ADRs for auth boundary, capability selection, data access, and failure semantics. Keep AGENTS.md brief and route specialized work to explicit skills.

Acceptance bar for "production-ready"

A fresh clone on the pinned toolchain must install from the committed lockfile, pass format/lint/type/test/build/audit gates, deploy its schema, reject unauthenticated mutations, keep server secrets out of client bundles, and publish no capability claim that lacks a test or implementation.
